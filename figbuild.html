Overview

This case study is in progress.

FigBuild is a design-to-build tooling project exploring how Figma's plugin ecosystem can close the intent gap in the designer-engineer handoff. The full case study is being documented as the project develops — check back soon. Below is the problem framing and early design direction.

System at a glance

Inputs Designer annotations: layout rules, token references, interaction specs, edge cases — attached directly to frames and components
Intelligence Structured annotation categories surface contextually in Dev Mode — the spec is always co-located with the design file, never out of sync
Outputs Engineers see categorized build notes — with inline token references that copy to clipboard — without leaving Dev Mode
Feedback loop Engineers flag missing or unclear annotations; designers update in place — the spec improves with each handoff cycle

Problem

Figma is built for designers. The handoff is an afterthought.

When engineers receive a Figma file, they're handed outputs without intent. Dev Mode surfaces CSS properties and component variants — but not the reasoning behind layout decisions, the expected behavior at edge cases, or which token to use when the auto-value and the design token diverge. The spec always lives somewhere else: a Notion doc, a Slack thread, a person's memory.

The structural problem: designer intent is a verbal, ephemeral layer that never makes it into the file. FigBuild asks: what if it did?

Intent gap

Dev Mode surfaces properties without context — tokens, component hierarchy, and design reasoning are all invisible to the engineer

Co-location gap

Build decisions — constraints, edge cases, responsive rules — live outside the file; the spec drifts from the design with every revision

Clarification cost

Engineers spend 30–40% of implementation time on clarification questions — a cost that compounds across every component and every sprint

Research

The handoff breakdown is structural, not interpersonal.

Early research involved shadowing three engineering teams as they received and implemented design files. The most consistent finding: engineers weren't confused about what things looked like — they were confused about how they were supposed to behave, especially at boundaries, across states, and at smaller viewports.

Research synthesis — handoff friction map

Insight: the missing layer is build intent, not design spec

The problem isn't that engineers can't read Figma — it's that Figma doesn't carry the designer's reasoning. The spec engineers need isn't "what does this look like" — it's "what should this do, and under what conditions, and why did the designer make this choice." That's a different kind of documentation entirely.

Solution

Structured build notes, co-located with the design.

FigBuild is a Figma plugin that lets designers attach categorized build notes directly to frames, components, and variants. Notes are typed — layout rules, token references, interaction specs, edge cases — and surfaced contextually when an engineer enters Dev Mode on that frame. The spec is always in the file. It can't drift.

Core Flows

Two users, one shared source of truth.

Designer: annotating build intent

Select any frame or component, open FigBuild, and attach a structured note. Categories keep annotations consistent across team members and easy to filter. The annotation lives with the component — not in a linked doc that goes stale.

Designer flow — annotation panel

Engineer: reading build context in Dev Mode

In Dev Mode, a FigBuild sidebar panel shows all annotations attached to the selected frame, grouped by category. Inline token references copy to clipboard on click. The engineer has everything they need without switching context — no Notion, no Slack, no clarification request.

Engineer flow — Dev Mode panel

Reflection

In progress.

This project is actively being developed and tested with design teams. The core hypothesis: the best handoff tool is one that makes the designer's reasoning legible without requiring them to leave their existing workflow. Testing will validate whether the structured annotation model holds across different team sizes and design systems.

Full reflection and validation findings will be documented once a complete cycle is complete.
